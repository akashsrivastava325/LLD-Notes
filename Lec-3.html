Observer Design Pattern

Lecture 3  ·  Behavioral Pattern  ·  Push Model  ·  Pull Model
DEFINITIONObserver Pattern is a Behavioral Design Pattern. It automatically notifies dependent objects when the state of another object changes.
  • Observable / Publisher — Maintains state + list of observers. Notifies them on state change.
  • Observer / Subscriber — Wants to know when publisher's state changes. Performs its own logic after notification.
Weather Station | | state changes ↓ Notify all | ┌──┴──────────┐ ↓ ↓ Current Forecast Display Display
  • Weather App — Weather Station (publisher) notifies TV and Radio (observers) whenever weather changes.
  • Social Media — Instagram profile (publisher) notifies all followers (observers) whenever a new post is made.
Publisher → notifies → Observers whenever state changes
  • Observable / Publisher — Object whose state is being observed. e.g. WeatherStation
  • Observer / Subscriber — Object that wants to receive updates. e.g. CurrentDisplay, ForecastDisplay
  • State — Information maintained by the publisher. e.g. Temperature, Humidity
Observable | maintains observers | ┌─────────┴─────────┐ ↓ ↓ Observer 1 Observer 2
  • Observable provides — addObserver() · removeObserver() · notifyObservers()
  • Observer provides — update()

Without Observer Pattern, the Weather Station directly depends on every display. As displays grow, the publisher gets increasingly tightly coupled.

WeatherStation → CurrentDisplay WeatherStation → ForecastDisplay WeatherStation → FutureDisplay // tightly coupled — bad!
PROBLEMAs the number of observers grows, the publisher must be modified every time a new observer is added.
WeatherStation ↓ Observer (interface) / \ ↓ ↓ Current Forecast Display Display
KEY IDEAPublisher only knows "I have a list of observers." It doesn't need to know the detailed logic of every observer.
  • Push Model Publisher sends data — Publisher decides what data the observer receives and passes it in update(data)
  • Pull Model Observer fetches data — Publisher only says "something changed". Observer pulls what it needs.
KEY QUESTIONWho decides what data the Observer receives?

The Publisher sends the required data directly to the Observer.

Publisher | | data ↓ Observer
// Publisher decides what to send: observer.update(weatherData);
RECALLPUSH = Publisher PUSHES data to Observer.
// Data object sent by Publisher class WeatherData { private double temperature, humidity; public WeatherData(double temperature, double humidity) { this.temperature = temperature; this.humidity = humidity; } public double getTemperature() { return temperature; } public double getHumidity() { return humidity; } } // Observer interface interface WeatherObserver { void update(WeatherData data); // ← receives data directly } // Concrete Observers class CurrentDisplay implements WeatherObserver { @Override public void update(WeatherData data) { System.out.println("Current: " + data.getTemperature() + "°C"); } } class ForecastDisplay implements WeatherObserver { @Override public void update(WeatherData data) { System.out.println("Forecast: " + data.getTemperature() + "°C"); } } // Publisher class WeatherStation { private List<WeatherObserver> observers = new ArrayList<>(); private WeatherData weatherData; public void addObserver(WeatherObserver o) { observers.add(o); } public void removeObserver(WeatherObserver o) { observers.remove(o); } private void notifyObservers() { for (WeatherObserver o : observers) o.update(weatherData); // ← push data } public void setWeatherReading(double temp, double humidity) { weatherData = new WeatherData(temp, humidity); notifyObservers(); } }
  • Step 1 — Create Publisher — WeatherStation station = new WeatherStation(); → observers list starts empty
  • Step 2 — Create Observers — new CurrentDisplay() and new ForecastDisplay()
  • Step 3 — Subscribe — station.addObserver(currentDisplay) → station maintains the observer list
  • Step 4 — State Changes — station.setWeatherReading(30, 70) → creates WeatherData, calls notifyObservers()
  • Step 5 — Notification — loops through observers, calls observer.update(weatherData) on each
WeatherStation | ↓ notifyObservers() | ├──→ CurrentDisplay.update(data) └──→ ForecastDisplay.update(data)
public class Main { public static void main(String[] args) { WeatherStation station = new WeatherStation(); CurrentDisplay currentDisplay = new CurrentDisplay(); ForecastDisplay forecastDisplay = new ForecastDisplay(); station.addObserver(currentDisplay); station.addObserver(forecastDisplay); station.setWeatherReading(30, 70); // both notified station.removeObserver(forecastDisplay); station.setWeatherReading(32, 65); // only CurrentDisplay notified } }

The Publisher is pushing the data to every observer. The observer doesn't need to ask for it — it arrives automatically inside update(weatherData).

WeatherStation | | WeatherData ← pushed by publisher ↓ CurrentDisplay
station.removeObserver(forecastDisplay); // Now only CurrentDisplay is in the list station.setWeatherReading(32, 65); // → only CurrentDisplay.update() is called
BENEFITObservers can unsubscribe at any time. Publisher doesn't need to be modified.

The Publisher only tells the Observer that something changed. It does NOT send the actual data. The observer fetches whatever it needs.

Publisher | | "Something changed" ↓ Observer | | fetch data ↓ Publisher
// Push — data sent in parameter: observer.update(weatherData); // Pull — no data, just a ping: observer.update();
RECALLPULL = Observer PULLS data from Publisher.
// Observable interface interface WeatherObservable { void addObserver(WeatherObserver o); void removeObserver(WeatherObserver o); void notifyObservers(); double getTemperature(); double getHumidity(); } // Observer interface interface WeatherObserver { void update(); // ← no parameters } // Publisher class WeatherStation implements WeatherObservable { private List<WeatherObserver> observers = new ArrayList<>(); private double temperature, humidity; @Override public void addObserver(WeatherObserver o) { observers.add(o); } @Override public void removeObserver(WeatherObserver o) { observers.remove(o); } @Override public double getTemperature() { return temperature; } @Override public double getHumidity() { return humidity; } @Override public void notifyObservers() { for (WeatherObserver o : observers) o.update(); // ← just a ping, no data } public void setWeatherReading(double temp, double humidity) { this.temperature = temp; this.humidity = humidity; notifyObservers(); } } // Observer — holds reference to publisher and fetches what it needs class CurrentDisplay implements WeatherObserver { private WeatherObservable weatherStation; // HAS-A reference public CurrentDisplay(WeatherObservable ws) { this.weatherStation = ws; ws.addObserver(this); } @Override public void update() { double temp = weatherStation.getTemperature(); double humidity = weatherStation.getHumidity(); System.out.println("Current: " + temp + "°C, Humidity: " + humidity + "%"); } } class ForecastDisplay implements WeatherObserver { private WeatherObservable weatherStation; public ForecastDisplay(WeatherObservable ws) { this.weatherStation = ws; ws.addObserver(this); } @Override public void update() { // Only pulls what IT needs — just temperature System.out.println("Forecast: " + weatherStation.getTemperature() + "°C"); } }
  • Step 1 — Observer stores publisher reference — private WeatherObservable weatherStation; → observer HAS-A publisher
  • Step 2 — Observer self-registers — Inside constructor: ws.addObserver(this)
  • Step 3 — State changes — station.setWeatherReading(30, 70) → publisher updates its fields, calls notifyObservers()
  • Step 4 — Publisher pings — observer.update() — no data sent
  • Step 5 — Observer pulls — calls weatherStation.getTemperature() and getHumidity() itself
WeatherStation ↑ | getTemperature() ← observer pulls what it needs | getHumidity() CurrentDisplay
public class Main { public static void main(String[] args) { WeatherStation station = new WeatherStation(); // Observers register themselves in their constructors CurrentDisplay current = new CurrentDisplay(station); ForecastDisplay forecast = new ForecastDisplay(station); station.setWeatherReading(30, 70); station.setWeatherReading(32, 65); } }
// Inside notifyObservers(): for (WeatherObserver o : observers) o.update(); // ← NO data here // NOT: o.update(weatherData);

The publisher simply says: "Something changed. You can check if you need anything." It doesn't decide what the observer should read.

// Inside CurrentDisplay.update(): double temperature = weatherStation.getTemperature(); double humidity = weatherStation.getHumidity(); // Inside ForecastDisplay.update(): double temperature = weatherStation.getTemperature(); // ForecastDisplay only needs temperature — pulls only that

Each observer fetches exactly what it needs. CurrentDisplay pulls both. ForecastDisplay pulls only temperature. Observer is in control.

  • Use Push when — Publisher should control exactly what data the observer receives. All observers need the same data fields.
  • Use Pull when — Different observers need different subsets of data. Observer should decide what information it needs.
// Pull is better when observers have different needs: CurrentDisplay → needs temperature + humidity ForecastDisplay → needs only temperature StatisticsDisplay→ needs temperature + humidity + history

The Pull Model connects directly to the HAS-A relationship from Lecture 1.

private WeatherObservable weatherStation; // HAS-A reference CurrentDisplay ↓ HAS-A ↓ WeatherObservable
CONNECTIONObserver HAS-A reference to Observable (Aggregation — both can exist independently).
  • Loose Coupling — Publisher only knows the WeatherObserver interface, not the concrete implementations
  • Easy to Add Observers — Add CurrentDisplay, ForecastDisplay, StatisticsDisplay, MobileDisplay without changing the notification mechanism
  • Easy to Remove Observers — removeObserver(observer) unsubscribes without affecting others
  • Automatic Notification — No observer needs to continuously poll/check for changes. State change → notifyObservers() → all observers react

RECALLOne-to-many relationship. Publisher changes → all registered observers automatically notified.
INTERVIEWObserver Pattern establishes a one-to-many relationship between a publisher and its subscribers. Whenever the publisher's state changes, it automatically notifies all registered observers. The notification can follow either a Push model (publisher sends the data) or a Pull model (observer fetches the required data from the publisher).
  • Category — Behavioral Design Pattern
  • Publisher — addObserver() · removeObserver() · notifyObservers()
  • Observer — update() or update(data)
  • Push — Publisher decides what to send · update(data)
  • Pull — Observer decides what to fetch · update() + HAS-A reference to publisher
