Low Level Design

Lectures 1–2  ·  SOLID Principles  ·  Design Patterns  ·  Relationships

LLD (Low Level Design) focuses on classes, objects, and how they relate and interact with each other. It sits between High Level Design and actual code.

LevelFocus
HLDOverall system architecture
LLDClasses, objects & their relationships
CodeActual implementation
GOALClean · Flexible · Maintainable · Testable code
  • HLD — Parking system, Payment system, Entry system, Exit system
  • LLD — ParkingLot, ParkingSpot, Vehicle, Ticket, Payment classes + their relationships
  • Code — Implement those classes in C++/Java
KEYDesigning properly is more important than just writing code. Clear design = easier coding.

A design pattern is a tested, reusable solution to a commonly occurring design problem. It prevents reinventing the same solution.

NOTEPatterns are helpful but NOT mandatory. Your design just needs to follow good principles — patterns already do.
  • Creational How objects are created — Singleton, Builder, Factory, Abstract Factory, Object Pool, Prototype
  • Structural How classes/objects are arranged — Adapter, Decorator, Proxy, Composite, Bridge, Facade, Flyweight
  • Behavioral How objects communicate — Controls coordination and responsibility between objects

Controls how objects are created. Singleton example: only one object exists, same object is always returned.

class Database { private static Database instance; private Database() {} public static Database getInstance() { if (instance == null) instance = new Database(); return instance; } }
RECALLCreational = How do I create the object?

Focus on how classes and objects are arranged/connected. Think of it as the skeleton of the system.

Car ├── Engine ├── Wheel ├── Headlight └── Steering

The question is not "how to create Engine?" but "how should Engine, Wheel, Headlight, Steering be arranged to build Car?"

RECALLStructural = How are objects/classes connected?

Focus on how objects communicate and interact.

Class A, Class B, Class C B → C // direct B → A → C // via intermediary
RECALLBehavioral = How do objects communicate?

IS-A = Inheritance / Parent-Child relationship

Vehicle ├── TwoWheeler // TwoWheeler IS-A Vehicle └── FourWheeler // FourWheeler IS-A Vehicle Employee ├── Manager // Manager IS-A Employee └── CEO // CEO IS-A Employee
class TwoWheeler extends Vehicle {}
RECALLIS-A = Inheritance

HAS-A = Association / Object relationship. One object contains or knows about another.

House HAS-A Room Library HAS-A Book School HAS-A Student
class Library { List<Book> books; // Library HAS-A Book }

HAS-A further splits into Aggregation and Composition.

Weak HAS-A relationship. Both objects can exist independently.

Library ◇──── Book // Library destroyed → Book still exists ✓
class Library { List<Book> books = new ArrayList<>(); // Book exists outside public void addBook(Book book) { books.add(book); } }
  • UML: Hollow diamond ◇
  • Independent lifetime — yes
RECALLAggregation = Weak HAS-A = Both can live independently

Strong HAS-A relationship. Child's existence depends on the parent.

House ◆──── Room // House destroyed → Room destroyed too ✗
class House { private final Room room = new Room(); // House owns Room's lifecycle }
  • UML: Filled diamond ◆
  • Lifecycle dependency — yes

SOLID is a set of fundamental design principles for creating clean, flexible, maintainable, testable, less duplicated code.

S → Single Responsibility Principle O → Open/Closed Principle L → Liskov Substitution Principle I → Interface Segregation Principle D → Dependency Inversion Principle
NOTEDesign patterns are not mandatory — but whatever design you create should follow principles like SOLID.
DEFINITIONA class should have only one reason to change. One class = one responsibility.
class Invoice { void calculateTotal() {} // business logic void saveToDB() {} // database logic void printInvoice() {} // printing logic } // ← 3 responsibilities in 1 class
  • Tax changes → modify Invoice
  • DB changes → modify Invoice
  • Print format changes → modify Invoice
  • Result: more testing, more bugs, harder maintenance
class Invoice { void calculateTotal() {} } class InvoiceRepository { void saveToDB(Invoice i) {} } class InvoicePrinter { void print(Invoice i) {} }
BENEFITDB logic changes → only InvoiceRepository changes. Invoice & InvoicePrinter untouched.
SRP ≠One method per class. That causes class explosion.

A class can have multiple methods if they belong to the same responsibility.

class InvoiceCalculator { double calculateSubtotal() {} // all related to double calculateTax() {} // invoice calculation double calculateTotal() {} // → ONE responsibility ✓ }
DEFINITIONOpen for extension, closed for modification. Add new functionality without touching already tested code.
class InvoiceDAO { void saveToDB() {} // SQL void saveToFile() {} // file void saveToNoSQL() {} // NoSQL ← keep adding = keep modifying! }

Every new storage option modifies existing, possibly deployed code. More risk of bugs in production.

interface InvoiceDAO { void save(); } class DatabaseInvoiceDAO implements InvoiceDAO { public void save() {} } class FileInvoiceDAO implements InvoiceDAO { public void save() {} } class CloudInvoiceDAO implements InvoiceDAO { public void save() {} } // ↑ new storage = new class, no existing code touched
RECALLOCP = Add new behavior by extending, not by modifying existing code.
DEFINITIONAn object of a superclass should be replaceable by an object of its subclass without breaking the application.
// If B IS-A A, then: A obj = new B(); // should still work correctly
abstract class Bike { abstract void turnOnEngine(); abstract void accelerate(); } class Bicycle extends Bike { void turnOnEngine() { throw new UnsupportedOperationException(); } // ← no engine! void accelerate() { /* pedal */ } }

Client calls bike->turnOnEngine() — works for Motorcycle, crashes for Bicycle. LSP violated.

interface Engine { void turnOnEngine(); void turnOffEngine(); } interface Bike { void accelerate(); void applyBrake(); } class Motorcycle implements Bike, Engine { /* has engine */ } class Bicycle implements Bike { /* no engine forced */ }
RECALLDon't make a child support behavior the parent promises but the child cannot provide.
DEFINITIONClients should not be forced to implement interfaces/functions they don't need. Keep interfaces small and focused.
interface RestaurantEmployee { void takeOrder(); void serveDrinks(); // waiter stuff void cleanKitchen(); // maintenance stuff void prepareFood(); void decideMenu(); // chef stuff — Waiter forced! } class Waiter implements RestaurantEmployee { public void prepareFood() { throw new UnsupportedOperationException(); } // forced → ISP violation }
interface WaiterTask { void takeOrder(); void serveDrinks(); } interface ChefTask { void prepareFood(); void decideMenu(); } interface MaintenanceTask { void cleanKitchen(); } class Waiter implements WaiterTask { /* only what it needs ✓ */ }
RECALLISP = Keep interfaces small and focused.
PrincipleFocusMain QuestionExample
LSPBehavior / substitutabilityCan I replace parent object with child without breaking client?Motorcycle → Bicycle breaks

LSP → Replacement ISP → Interface
DEFINITIONHigh-level components should not depend on low-level components. Both should depend on an abstraction.
// Bad: High Level Class → Concrete Low Level Class // Good: High Level Class → Interface ← Low Level Classes
class MacBook { private WiredKeyboard keyboard = new WiredKeyboard(); // ← tightly coupled! public void type() { keyboard.type(); } } // Want Bluetooth? Must modify MacBook.
interface Keyboard { void type(); } class WiredKeyboard implements Keyboard { public void type() {} } class BluetoothKeyboard implements Keyboard { public void type() {} } class MacBook { private Keyboard keyboard; // ← depends on abstraction ✓ public MacBook(Keyboard kb) { this.keyboard = kb; } public void type() { keyboard.type(); } }

MacBook doesn't care if it's Wired, Bluetooth, or any future keyboard type.
